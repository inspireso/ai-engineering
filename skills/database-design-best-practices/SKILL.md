# 数据库设计最佳实践

## 概述

关系型数据库设计规范。涵盖字符集、建表、索引、SQL 编写和 ORM 映射。设计目标：**一致性、可维护性、性能**。

> **来源**：提炼自 [MySQL 数据库](https://suyuanzhili.feishu.cn/wiki/Yjm2wYr8Ni9Uskk0aM5cR7RKnef)，泛化至多数据库。

## When to Use

| 触发场景 | 不适用 |
|----------|--------|
| 设计新表结构、CREATE TABLE | 慢查询排查、运行时 SQL 调优 |
| 创建索引、review 索引设计 | 线上事故应急 |
| 编写 SQL 语句、ORM 映射 | 已有系统的迁移方案制定 |
| 审查 DDL / 迁移脚本 | 数据库特定功能（如 PostgreSQL 扩展、Oracle 物化视图等） |

## 核心原则

1. **配置收敛于默认** — 实例级统一字符集和排序规则，不要在 DDL 中逐表/逐库覆盖，避免层次间不一致
2. **命名见名知义** — 表名/字段名/索引名遵循统一约定，一眼可辨类型和含义
3. **类型精准匹配** — 根据数据特征选择最合适的类型和长度，不过度也不妥协精度
4. **索引按需设计** — 以查询场景驱动索引创建，遵守最左前缀匹配，兼顾写入成本
5. **SQL 防御式编写** — 每个语句考虑 NULL 语义、隐式转换、分页边界、多表歧义

## 强制执行

违反以下任一规约即要求修改。

### 字符集与排序规则

- 字符集和排序规则在**实例级**统一配置（如 MySQL `utf8mb4` + `utf8mb4_0900_ai_ci`，PostgreSQL `UTF8` + `lc_collate`）
- DDL（建库、建表、迁移脚本）中**不得**显式覆盖字符集或排序规则——一律继承实例默认
- 新项目接入时，检查并统一修正历史遗留的不一致配置

### 命名规范

- 表名、字段名**必须**全小写，单词间用下划线分隔；禁止数字开头，禁止两个下划线中间只出现数字
- 表名**禁用**复数（`user`，非 `users`）；推荐 `业务前缀_表作用`（如 `cms_task`、`org_user`）
- 库名与应用名称尽量一致
- **禁用**所在数据库的保留字
- 布尔字段**必须** `is_xxx`，用最小整数类型（1 是 0 否）

### 字段类型

- 精确数值**禁止**使用近似浮点类型（`float`/`real`），用精确十进制类型（`decimal`/`numeric`）
- 定长字符串用定长类型；变长字符串长度控制在合理上限内；超大文本独立成表，用主键关联
- 非负整数字段**必须**加无符号约束（数据库支持时）或 check 约束
- 根据值域选择最小够用的整数宽度——不浪费存储，也不低估增长

### 必备字段

每张表**必须**包含：

- `id` — 自增主键，使用数据库支持的最大整型
- `create_time` — 创建时间，自动填入当前时间
- `update_time` — 更新时间，每次修改自动更新

例外：多对多纯关联表（仅含两个外键、无其他业务字段）可用复合主键替代独立 `id`，但仍需 `create_time` 和 `update_time`。

> 若团队或框架已有统一时间字段命名约定（如 Rails 的 `created_at`/`updated_at`），优先保持项目内一致。

### 逻辑删除

- **禁止**物理删除数据，**必须**使用逻辑删除标记（`is_deleted` 或 `deleted_time`）
- 例外：临时/会话数据（验证码、临时 token、缓存表、消息队列暂存表）可豁免此条——其生命周期由系统自动管理，无需审计追溯
- 注意逻辑删除可能破坏唯一约束的唯一性——需根据具体场景选择：状态字段、唯一索引包含删除标记、或应用层清理后恢复

### 索引

- 命名：主键 `pk_字段名`，唯一 `uk_字段名`，普通 `idx_字段名`（多字段用下划线连接）
- 业务唯一字段（含组合）**必须**创建唯一索引——**禁止**依赖应用层"先查后插"保证唯一性（并发下必然脏数据）
- 超过三个表**禁止** join；join 字段类型必须跨表绝对一致，被关联字段必须有索引
- 变长字符串建索引时按区分度选择性索引——短字段可直接全值索引，长字段通过前缀（MySQL）或函数索引（PostgreSQL/Oracle）避免全值索引的空间浪费；**唯一索引例外**——唯一索引需全值保证唯一性，不截断
- 组合索引：等号条件列前置，区分度高的列靠左
- 防止隐式类型转换——查询参数类型必须与字段类型匹配

### SQL 编写

- 多表查询中**每个列名**前必须加表别名限定，避免字段歧义
- 表别名使用 `as t1, t2, t3...` 按 JOIN 顺序命名
- **禁止**使用外键与级联——外键约束在分布式/高并发场景下是强阻塞，存在级联更新风暴风险；一切外键概念在应用层解决
- **禁止**使用存储过程——难以调试、扩展和移植
- `IN` 子句元素数量控制在 **1000 以内**（Oracle 硬限制；MySQL/PostgreSQL 同样建议），超过则分批

### 数据修改

- 数据订正（删除/修改记录）前**必须先 select**，确认影响范围无误后再执行更新
- 更新记录时**必须**同步更新 `update_time` 为当前时间——任何遗漏都视为违规

### ORM 映射

- 布尔字段命名：数据库 `is_xxx`，实体类属性 `xxx`（不加 is 前缀），在 ORM 映射中显式关联

## 推荐实践

以下可灵活调整，但需在 review 时说明原因。

- **字段冗余**：允许为提高查询性能适当冗余，前提——非频繁修改、非唯一索引、非超长变长串或大文本字段
- **分库分表**：单表超过 **5000 万行**或容量超过 **5GB** 时才推荐分；预计三年内达不到不提前分
- **覆盖索引**：高频查询字段尽量包含在索引内，避免回表——通过数据库执行计划工具验证
- **order by 有序性**：排序字段尽量放在组合索引末尾，利用索引有序性避免额外排序
- **性能目标**：优先索引查找，其次索引扫描，避免全表扫描
- **字段注释**：修改字段含义或追加状态值时，必须同步更新字段注释

## Red Flags — 看到立刻停

| 合理化借口 | 实际情况 |
|-----------|----------|
| "这个字段不太可能重复，唯一索引先不加" | 墨菲定律——并发下必然脏数据 |
| "先 float 用着，后面再改成 decimal" | 精度损失一旦写入无法恢复 |
| "这次直接物理删除，数据不重要" | 出了事故无法追溯 |
| "先用 SELECT * 把功能跑通" | 上线后大字段拖垮网络，改回来成本更高 |
| "只是原型/临时表，规范不适用" | 原型变生产的概率远超预期 |
| "这个 in 列表刚好 1001 个" | 1000 是硬上限，多 1 个也不行 |
| "测试库不需要字符集规范" | 测试与生产差异导致的问题上线才能发现 |
| "字段冗余加一个没关系" | 不满足三个条件的冗余字段终将成为数据不一致的来源 |

**以上任一出现：回到规范，按要求修改。没有例外。**

## 检查清单

做数据库设计 review 或编写 DDL 时，逐项确认：

- [ ] 字符集 — 实例级统一，DDL 不显式覆盖
- [ ] 命名 — 全小写、单数、无保留字、`is_xxx` 布尔字段、`业务前缀_表作用`
- [ ] 字段类型 — 精确数值用 decimal、变长串有上限、超大文本独立表、非负数约束、最小够用整数
- [ ] 必备字段 — `id`、`create_time`、`update_time` 齐全
- [ ] 逻辑删除 — 有删除标记字段，无物理删除
- [ ] 索引 — 命名 `pk_`/`uk_`/`idx_`、业务唯一字段有唯一索引、变长普通索引有前缀长度、组合列顺序合理、无隐式转换
- [ ] SQL — 表别名限定列名、无外键/级联、无存储过程、IN 元素 ≤ 1000、无 SELECT *
- [ ] 更新 — 先 select 确认、同步更新 `update_time`
- [ ] ORM — `is_xxx` → `xxx` 显式映射
